Interactive architecture map · RTL-grounded

Think of tiny-gpu as one instruction broadcast to many lanes.

The dispatcher hands a block to each core. A core shares its scheduler, fetcher, and decoder across up to four threads, while every thread keeps its own registers, ALU, LSU, and PC.

The core mental model: GPU → blocks → cores → threads/lanes. Program memory supplies one instruction stream; data memory supplies per-lane operands. Control is shared, data is lane-local, and memory is asynchronous.

03 · Inside a core

Control is shared; execution state is replicated per thread.

Every core executes one block at a time. Its scheduler, fetcher, and decoder are shared, while each enabled lane has its own register file, ALU, LSU, PC, and NZP state.

04 · One instruction

The core walks a six-state loop, not a CPU-style pipeline.

This implementation completes most of one instruction’s stages before fetching the next. Memory instructions stretch WAIT; arithmetic instructions usually pass through it immediately.

    05 · SIMD / SIMT mental model

    One instruction stream, four private register contexts.

    The lanes receive the same control signals but resolve different data because their register files and special registers differ. tiny-gpu assumes all lanes converge to one PC.

    What is shared, what is private?

    This is the distinction that unlocks the architecture: the core is not four independent CPUs. It is one control path with four replicated datapaths.

    1

    Shared: scheduler state, current PC, fetched instruction, decoded control signals.

    2

    Private: 16-register file, ALU result, LSU state, next-PC/NZP state.

    3

    Special registers: R13 = %blockIdx, R14 = %blockDim, R15 = %threadIdx. They let one program address different data per lane.

    4

    Simplification: per-thread PCs exist, but the scheduler advances using the last lane’s next_pc. Divergent branches are not supported.

    06 · Memory is the long pole

    Many lanes ask; a channel-limited controller serializes access.

    Each enabled thread has its own LSU, so one core can have four outstanding data-memory requests. The controller maps eight total LSU consumers onto four external read/write channels.

    Why WAIT exists

    LDR/STR are asynchronous. The core stays in WAIT until every active LSU leaves REQUESTING/WAITING.

    Why controllers exist

    They prevent eight LSUs plus fetchers from pretending external memory has unlimited ports.

    What is missing

    No cache, coalescing, bank model, or pipelined overlap. Each instruction’s memory latency is exposed.

    16-bit instruction format

    The decoder slices fixed bit ranges. Some opcodes reinterpret the middle bits as an immediate or branch mask.

    [15:12]opcode
    [11:8]destination register / branch mask
    [7:4]first source register
    [3:0]second source register

    CONST and BRnzp use instruction[7:0] as an 8-bit immediate.

    R0–R12general-purpose, writable, 8-bit
    R13%blockIdx — assigned by the dispatcher
    R14%blockDim — threads per block, fixed at 4 here
    R15%threadIdx — constant lane index
    08 · Keep these five ideas

    The mental model on one screen.

    1

    Blocks flow to cores

    The dispatcher does not run threads itself. It partitions thread_count into blocks and feeds idle cores.

    2

    Control is shared

    One scheduler, fetcher, decoder, instruction, and current PC drive all lanes in a block.

    3

    State is lane-local

    Registers, ALU, LSU, PC, and NZP are replicated. Special registers make each lane address different data.

    4

    Memory is asynchronous

    LSUs use valid/ready handshakes. Controllers multiplex many consumers onto few external channels.

    5

    It is deliberately simple

    No cache, no pipelining, no independent lane PCs, no branch divergence. Understand this machine before scaling up.
